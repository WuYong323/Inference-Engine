### 1.4 恢复 W8 的 Triton RMSNorm（本机只有笔记，20 分钟重写）

配套 `bench/triton_rmsnorm.py` 是从 Triton 官方教程惯例恢复的完整版（Meta 的 [applied-ai fused_rms_norm](https://github.com/meta-pytorch/applied-ai/blob/main/kernels/triton/training/rms_norm/fused_rms_norm.py) 是同款工业写法）。核心 12 行：

```python
@triton.jit
def rms_norm_kernel(X, Y, W, eps, H, BLOCK: tl.constexpr):
    row = tl.program_id(0)                       # 一个 program 负责一行（和你 Day1 的排布一致）
    X = X + row * H
    Y = Y + row * H
    offs = tl.arange(0, BLOCK)                   # 整行作为一个 BLOCK（Triton 教程惯例）
    mask = offs < H
    x = tl.load(X + offs, mask=mask, other=0.0).to(tl.float32)
    w = tl.load(W + offs, mask=mask, other=0.0).to(tl.float32)
    rms = tl.sqrt(tl.sum(x * x) / H + eps)       # 编译器生成归约树（warp shuffle）
    y = (x / rms * w).to(Y.dtype.element_ty)
    tl.store(Y + offs, y, mask=mask)
```

注意它和你手写 kernel 的**结构同构**：一行一个 program（≈ block）、块内归约、广播、第二遍。差异在"谁写细节"：你的 CUDA 手控 warp shuffle/合并/向量化；Triton 编译器代劳——**kernel 越简单，编译器优势越难发挥**（这是 §2.3 预测的第一条依据）。

### 1.5 工业规范：打包上机的标准姿势

## 2. 四方对标：四个对手的公平竞技场（5h）

### 2.1 四方是谁、各自"赢的原理"是什么

| 对手 | 是什么 | 它的优势来源 | 它的代价 |
|---|---|---|---|
| **torch eager** | 普通 Python 调用链，逐算子发射 | 无（基线） | 每个算子一次 launch + 中间张量全落显存：访存次数 × launch 次数双高 |
| **torch.compile** | TorchInductor 编译器：图捕获 → 算子融合 → Triton 代码生成 | **全图融合**：把相邻算子融成一个 kernel | 编译时间、动态形状受限 |
| **Triton (W8)** | Python DSL，block 级编程，编译器自动向量化/合并/流水线 | 开发效率 + 编译器优化（autotune 可选） | kernel 简单时编译器优势发挥不出来 |
| **你的 CUDA** | Day 1–4 的手写变体（reread/vec4/stash + fused） | 手控一切 + Day 2/3 的手工配置 | 开发成本最高 |

**关键概念——torch.compile 的"全图融合（whole-graph fusion）"**：TorchInductor 不只优化单个算子，它把计算图里**相邻的算子融成一个 kernel**。所以 torch.compile 的对手不是"你的 rmsnorm"，而是"你的 rmsnorm + 它前后的算子"。**这就是"分母不同"（下面 §2.3 的 caveat）的技术根源。**

### 2.2 竞技场设计：两个战场 × 两种分母

**两个战场**（对应 Day 2 扫描的两个区间）：

- **prefill (16384, 4096)**：带宽战场——grid 巨大、memory-bound，比的是"谁更贴近 %peak"；
- **batch decode (32, 4096)**：并行度战场——一波装不满（Day 2 §1.4 的尾波区），比的是"谁更扛 launch 与低并行度"。

**三尺子**（复用 W1 Day2 `bench_harness.compare()`，全部记录）：

- `allclose`：过不过（二元判决）；
- `cosine`：整体"方向"对不对——掉到 0.99 以下通常是算法错而非精度问题；
- `max_abs + max_rel`：最坏点差多少——定位精度类差异。

**★ 竞技场设计升级（把 caveat 变成实验）**：除了"单算子四方"，再加一个**融合链战场**——`torch.compile(add + rmsnorm)` 对 **你的 `fused_add_rmsnorm`（Day 4 的 kernel）**。这样当**分母相同**（都是 1 个 kernel、同样访存量）时，手写 CUDA 与 Inductor 的**公平对决**才成立；同时单算子战场里 compile 的"胜利"会自动现形为"它融合了更多东西"。配套 `bench/fourway.py` 已按此设计实现。

| 战场 | 我预测的赢家 | 推理链（必须写满） | 实测 | 对了吗 |
|---|---|---|---|---|
| prefill 单算子 | | | | |
| prefill 融合链 | | | | |
| decode 单算子 | | | | |
| decode 融合链 | | | | |

**导师的预测（供对赌，先自己写）**：

> **prefill 单算子：你的 CUDA 与 Triton 打平或略胜**——这个 kernel 太简单，Triton 编译器的优势发挥不出来，而你的手工配置（vec4 + 最优 block）是 Day 2/3 真金白银扫出来的。**torch.compile 在"单算子"下 ≈ Triton 水平（它也只生成一个 kernel）；但在"融合链"下会赢**——它把 add+rmsnorm 融成一个 kernel，分母变成一段图。
>
> **如果 torch.compile 赢了，那不是你的失败，是"分母认知"**：你在比"单个算子"，它在比"一段图"。W8 你已经得出过这个结论，今天是在 CUDA 层面再验证一次。**在笔记里明确写出这个 caveat——诚实标注对手的优势来源，是你最值钱的学术素养**（审稿人看到"我清楚对手为什么赢"，会立刻把你和"报喜不报忧"的论文区分开）。

### 2.4 完整对标脚本（配套 `bench/fourway.py`）

```python
# 单算子战场（分母 = 1 个 rmsnorm kernel）
impls = {
    "eager":           lambda: rmsnorm_torch(x, w),
    "compile(single)": lambda: compiled_single(x, w),   # 编译单个算子：没有融合对象
    "triton":          lambda: rmsnorm_triton(x, w),
    "cuda/vec4/b512":  lambda: CudaBackend(block=512, variant="vec4").rmsnorm(x, w),
    #                                              ↑ block 取你 Day3 扫描表的最优值，别拍脑袋
}
for name, fn in impls.items():
    cmp = compare(fn(), ref, name)                      # 三尺子
    r = bench_op(f"{name}/rmsnorm/{rows}x{H}", fn, bytes_moved=2*rows*H*4)
    ...

# 融合链战场（分母 = add+rmsnorm 一段图；三个实现的访存下界都是 4×rows×H×4）
def chain_eager(res, a): return rmsnorm_torch(res + a, w)          # 5 次访存（真实流量）
chain_compile = torch.compile(chain_eager)                        # 全图融合机会
def chain_cuda(res, a): return fused_add_rmsnorm(res, a, w, ...)   # Day4 kernel：4 次访存
```

运行与记录：结果全部落 `research/data/fourway_{tag}.json`，三尺子逐行记录——**性能数字和三尺子缺一个，这个数就不可信。**

### 2.5 结果解读框架（拿到数据后照做）

1. **每个战场单独判赢家**——不要把两个战场混成一个"总分"（带宽战场和并行度战场是两种物理）；
2. **每家的"优势来源"写一列**：eager 输在访存×launch；compile 赢在融合；Triton 与你在单算子上贴身肉搏；
3. **caveat 正式落笔**："compile 的胜利来自分母不同（一段图 vs 一个算子）；在融合链战场（同分母）上，我的 fused kernel 与 Inductor 的差距才是手写 CUDA 的真实水平。"

## 3. ncu 四组指标：每组回答一个问题（延续 W1 Day6 方法论）

**方法论重申（W1 Day6 的纪律）**：一组指标回答一个问题，不无脑 `--set full`——指标山会淹没结论。四问四组：

```bash
# ① 我在 Roofline 的哪里？
ncu --metrics dram__bytes.sum.per_second,sm__throughput.avg.pct_of_peak_sustained_elapsed \
    -k regex:rmsnorm python bench/fourway.py

# ② occupancy 实测 vs 手算
ncu --metrics sm__warps_active.avg.pct_of_peak_sustained_active \
    -k regex:rmsnorm python bench/fourway.py

# ③ 访存合并度（每次请求几个 sector）
ncu --metrics l1tex__average_t_sectors_per_request_pipe_lsu_mem_global_op_ld.ratio \
    -k regex:rmsnorm python bench/fourway.py

# ④ 有没有寄存器溢出（stash 版本要特别看）
ncu --metrics l1tex__t_sectors_pipe_lsu_mem_local_op_ld.sum,l1tex__t_sectors_pipe_lsu_mem_local_op_st.sum \
    -k regex:rmsnorm python bench/fourway.py
```

**每组指标怎么读**：

1. **① Roofline 位置**：`dram__bytes.sum.per_second` = 实测 DRAM 带宽（对照你的 `%peak`）；`sm__throughput...pct_of_peak` = SM 利用率。两者组合定位：带宽高 + SM 低 = memory-bound（Day 2 判据的 ncu 版）；H100 的 ridge = 989 TFLOPS / 实测带宽（~3.1 TB/s）≈ **320 FLOP/B**，rmsnorm 的 AI≈0.5 ≪ 320 → 恒 memory-bound。
2. **② achieved occupancy**：和 Day 2 的手算/API 三方对齐，在 H100 上重做一遍（2048 threads/SM = 64 warps——**同样的 BLOCK=256 在 H100 上最多住 8 个 block**，5060 是 6 个，阈值表整张平移）。
3. **③ 合并度（coalescing）**：先懂 **sector（扇区）**——L1/L2 与显存之间的传输单位是 **32 字节**。理想情况下一个 warp 的 32 个线程访问 32 个连续 float = 128 B = **4 个 sector**，一次请求恰好用满；float4 版本 = 512 B = **16 个 sector**。这个 ratio 指标就是"每次请求平均用了几个 sector"——**float 版接近 4.00、vec4 版接近 16.00 就是完美合并**，明显偏大 = 有浪费的 sector（未合并访问）。
4. **④ 寄存器溢出**：`local_op_ld/st` 是 **local memory（寄存器溢出的 DRAM 备份）**的流量。**stash 版本重点看**——Day 3 的伏笔在 H100 上兑现：H100 的 regs/SM 也是 65536 但线程槽位 2048，EPT 的租金账（阈值表）完全不同，溢出与否用这两个指标一锤定音。

### 4.3 为什么会有损失（机制，写进论文 method 的素材）

三处架构差异，各自移动最优配置：

1. **线程槽位**：1536 vs 2048 threads/SM → Day 2 的 occupancy 阈值表整张平移（5060 上 BLOCK=256 住 6 块，H100 住 8 块）；
2. **SM 数与带宽**：26 vs 132 个 SM、325 vs ~3100 GB/s → 波次计算、尾波损失完全不同（32 行的形状在 5060 上一波装不满，在 H100 上一波绰绰有余）；
3. **Little's Law 缺口**：Day 2 算过——H100 每线程 4 B 时在途缺口 2.2 倍（5060 只差 2%）→ **向量化（vec4）在 H100 上比在 5060 上更关键**，最优 variant 可能随架构翻转。

**这三条就是 Day 6 cost model 的"跨架构项"——今天先拿数据，明天建模型。**

### 4.4 研 A（30 min，顺手做）：AMK 巨核的 occupancy 分析

用这周学的眼光给师兄打工：从 AMK 的 ncu 数据读出巨核 kernel 的**寄存器/shared 用量**，用 Day 2 的 `occupancy_worksheet.py`（H100 常数）算它的**理论 occupancy**。

**为什么这个发现值钱**：巨核（megakernel）把几十个算子塞进一个 kernel → 寄存器需求暴涨 → 每个线程的 regs 冲到上百 → occupancy 被寄存器压到 25–50% → 延迟隐藏变差——**巨核自己的性能上限就卡在寄存器上**。如果数据证实"巨核因寄存器压力 occupancy 很低"，这是师兄会很想要的发现（他的论文缺的正是这种机制级分析）。**成本 30 分钟，关系收益很大——顺手做，别当主业。**

## 6. 完成标准自测（两道题，先默写再对答案）

1. **四方各自赢在哪、输在哪？"分母不同"这个 caveat 是什么？**
   *答案要点*：eager 输在逐算子 launch + 中间张量全落显存（访存×launch 双高）；torch.compile 的优势来源是**全图融合**（Inductor 把相邻算子融成一个 kernel）——它比的是"一段图"，你比的是"一个算子"，**分母不同**；Triton 靠编译器代劳细节，kernel 简单时优势发挥不出来，prefill 上你的 CUDA（手控 vec4 + 扫描出的最优 block）应与其打平或略胜；公平对决在**融合链战场**（你的 Day 4 fused kernel vs compile(add+rmsnorm)，同分母）。诚实标注对手优势来源是最值钱的学术素养。
2. **跨架构表填满后，一句话说出"配置可移植性"这个问题真不真？**
   *答案要点*：看移植损失列——≥20% 是真问题（换卡调参作废、autotune 重跑，你的零试跑方法有存在理由）；~2% 是路不通（转测量类框架，一套数据两种形态）。机制上有三条支持"不可移植"：线程槽位平移 occupancy 阈值表、SM 数/带宽改变波次与尾波、Little's Law 缺口（H100 上向量化更关键）——但**判决靠今天的表，不靠机制推理**。

## 附 A：术语速查表（Day 5）

| 名词 | 一句话解释 |
|---|---|
| torch.compile / TorchInductor | PyTorch 编译器：图捕获 → 算子融合 → Triton 代码生成 |
| 图捕获（graph capture） | 把 Python 调用链记录成计算图，供编译器整体优化 |
| 全图融合（whole-graph fusion） | Inductor 把相邻算子融成一个 kernel——compile 的优势来源（"分母不同"的根源） |
| Triton | Python DSL 写 GPU kernel，编译器自动向量化/合并/流水线 |
| 四方对标 | eager / torch.compile / Triton / 手写 CUDA 的同台比较 |
| 三尺子 | allclose（过不过）/ cosine（方向）/ max_abs+max_rel（最坏点） |
| sector（扇区） | L1/L2 与显存间的 32B 传输单位；合并度按"每请求几个 sector"衡量 |
| coalescing（访存合并） | warp 的访问落在连续地址、sector 零浪费；理想 float=4、float4=16 |
| Roofline 位置 | 用 DRAM 带宽% + SM 利用率% 定位 kernel 在屋顶线的哪段 |
| local memory（本地内存） | 寄存器溢出的 DRAM 备份；`local_op_ld/st` 指标暴露它 |
| 跨架构可移植性 | 一张卡的最优配置在另一张卡上损失多少——今天判决的问题 |
| gpu-tag | 输出文件名的卡型标签，保证两卡数据并存（可追溯纪律） |
| 分母不同（caveat） | 对手在比"一段图"而你在比"一个算子"——诚实标注对手优势来源 |
| 巨核（megakernel） | 多算子融成一个 kernel（AMK 线）；寄存器压力是其 occupancy 上限 |
| dry-run | 上机前本地预演全部脚本（集群时间纪律） |
| 独占窗口 | 集群上无邻居抢占的时段——校准/正式测量的前提 |
